Hadoop 1.x 实验笔记：把一次作业跑起来

Raymond / 2016.01.09

文章目录＋
  1. 先确认三个环境
  2. 配置按职责分开
  3. 先观察守护进程，再提交任务
  4. 区分本地路径与 HDFS 路径
  5. 重启与格式化不是一回事

最初学习 Hadoop 时，我花了不少时间在算法之外：环境变量是否生效、节点能否互相连接、程序究竟读取了哪一份配置。这里把当年的实验重新整理成一条能回忆起来的路径。

实验基于 Hadoop 1.0.4 与当时的 Java 环境。本文保留 1.x 的进程模型，作为历史学习笔记；后续版本的部署方式不应直接照搬。

先确认三个环境

第一是 Java 环境。命令行使用的 Java、Hadoop 脚本配置的 JAVA_HOME 以及实际安装目录应该一致。

第二是节点间通信。实验节点需要能解析彼此的主机名，并使用预期的账户连接。示例中统一使用 worker-a、worker-b 这类名称，实际环境的账号和地址不属于算法配置。

第三是 Hadoop 的配置目录。当时反复出错的地方，就是修改了实验目录里的配置文件，程序却仍读取安装目录的默认配置。

变量值只是目录示例，关键是让启动脚本与提交任务的终端使用同一份配置。

配置按职责分开

在当时的 1.x 环境里，core-site.xml 保存通用设置，hdfs-site.xml 描述文件系统，mapred-site.xml 描述 MapReduce 配置；节点清单另外保存。

实验还把训练结果路径作为自定义配置传给程序。比起把路径散落在源码里，通过配置读取更方便切换不同输入，也便于复现。

先观察守护进程，再提交任务

Hadoop 1.x 的实验里，需要分别检查文件系统和计算调度相关进程。NameNode、DataNode 与 JobTracker、TaskTracker 承担不同职责：文件能写进去，不代表计算节点已经可用。

进程列表只是第一步。还要看日志和状态页面，确认节点确实注册成功，而不是启动后立即退出。

区分本地路径与 HDFS 路径

本地创建的输入文件不会自动出现在 HDFS。需要先上传，再把 HDFS 路径交给作业。

同样，输出目录通常要求在任务开始前不存在。这个约束能防止程序不小心覆盖已有结果，也是第一次跑 WordCount 时很容易遇到的报错。

重启与格式化不是一回事

实验中曾误把格式化当作重新启动的一部分。格式化会涉及文件系统元数据，不能作为普通故障的默认处理步骤。

遇到节点不能启动、文件操作受限或者安全模式提示，应先阅读日志，确认配置、目录状态和数据节点情况。只有明确知道自己在初始化一个可丢弃的实验环境时，才考虑重新建立文件系统。

这次作业留下的经验，是先把环境、配置和数据位置理清，再讨论分布式程序本身。很多看起来像框架故障的问题，实际发生在这些边界上。
