Android 动态加载：把计算任务作为插件

这次实验希望让 Android 程序在运行时加载新的计算任务，而不是每加一种任务都重新打包整个应用。任务只需要计算能力，不需要插件界面，这让问题可以先缩小到类加载与接口调用。

先区分两种执行方式

一种方式是把任务作为独立程序执行，自己处理入口、输入和输出；另一种方式是在已有进程里加载任务类，通过对象和方法调用完成计算。

后者更容易复用宿主的调度、日志和通信能力，也是这篇笔记主要讨论的路线。

普通 class 文件还不是 Android 可加载任务

在当时的实验工具链中，Java 编译产生的 class 需要进一步转换成 Android 运行时使用的 DEX 表示。文件外层虽然可能是 JAR 或 APK，但真正需要确认的是里面是否包含目标运行环境能够加载的代码。

因此，看到扩展名是 .jar，不能直接判断它适合拿给 Android 的类加载器。

共享接口应由宿主的类加载路径提供。插件可以在编译时依赖它，但不应再携带一份由另一个加载器定义的副本，否则即使类名相同，也可能不能完成预期的类型转换。

类的身份还包含类加载器

在讨论动态加载时，只记住完全限定类名是不够的。类由哪个加载器定义，同样影响运行时类型身份。

这也是为什么“重新创建一个加载器，再加载同名类”并不等价于“把原对象变成新版本”。旧对象仍属于原来的类型，新对象必须通过稳定的共同接口与宿主交互。

DexClassLoader 只是其中一环

实验使用 DexClassLoader 加载转换后的任务。这里需要明确代码路径、运行时所需目录以及父加载器的关系。

典型的父级委派会先尝试已加载的类和父加载器，再寻找自身可提供的类。实际行为受实现与平台版本影响，不能简单地认为“磁盘上的文件变了，下次 loadClass 就会换成新版本”。

如果要更新插件，需要额外设计版本、任务生命周期和旧对象退出机制。

反射还是接口调用

反射适合探索一个未知类，或者调用一个很小的约定入口；接口调用则把约定提前到了编译阶段，方法签名、异常以及数据格式更清晰。

对计算任务，我更倾向于把反射限制在构造阶段，随后转为共享接口。这样调度器只处理 ComputeTask，不需要知道每个插件的具体类名和方法细节。

计算插件与界面插件的难度不同

能够加载一个普通类，不代表就能直接运行完整 Activity。组件注册、生命周期、资源、主题和上下文都会引入额外约束。

这次实验没有涉及界面资源加载，因此不能据此得出“完整应用插件化已解决”的结论。先把计算任务的边界做好，比把所有插件化问题一起引入更可控。

动态任务需要可信来源与失败隔离

任务包的来源、版本和完整性应被明确记录。动态执行与宿主同进程代码，通常也意味着它获得了宿主的运行环境，而不是天然处在一个安全沙箱里。

在调度层，还要规定超时、取消、失败重试与结果格式。类能被加载只是第一步，真正的并行任务系统还需要回答：一项任务失败后，其他任务是否能够继续。
