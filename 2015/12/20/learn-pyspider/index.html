一次爬虫框架选型与调试记录

最初接触爬虫时，我以为问题只是“请求网页，再把需要的字段解析出来”。真正做起一个采集实验，才发现任务调度、动态页面、失败重试和结果处理会占去更多时间。

这篇保留的是早期使用 pyspider 的经历，其中的工具和浏览器组件属于当年的环境，适合回看选型思路，不宜照着版本清单直接部署。

先把需求拆开

实验需要定期更新数据，希望能方便地增加采集任务，也希望在出错时直接看到请求和处理结果。对我而言，调试界面和可观察性与吞吐量同样重要。

当时先尝试了 Scrapy。对于普通 HTML 页面，处理流程很清晰；遇到依赖 JavaScript 的页面后，则需要再判断：数据是否来自可以直接访问的接口，还是必须执行浏览器脚本。

这两条路线的成本不同。分析接口通常更轻，但需要理解请求参数与状态；浏览器渲染更接近实际页面，却会消耗更多内存、时间和并发资源。

为什么后来尝试 pyspider

当时的 pyspider 将脚本编辑、任务状态和结果查看放进了 Web 控制台。对于刚上手的人，这种反馈很直接：发起一次请求，就能看到页面、解析字段和后续任务是否符合预期。

另一个有用的特点是组件分离。调度、抓取、处理与结果保存各自承担职责。遇到数据不更新，不必一开始就怀疑所有代码，可以先确认任务有没有被调度，再看抓取是否成功，最后检查解析和落库。

动态页面的瓶颈往往在浏览器

实验中出现过浏览器工作进程不稳定的情况。降低请求速率、限制并发，再观察进程内存与失败率，比直接增加工作进程更有帮助。

增加抓取进程并不必然提高整体速度。如果浏览器已经成为瓶颈，队列堆积只会让任务等待更久。合理的做法是分别测量请求耗时、页面执行耗时和结果处理耗时，再决定扩容哪一部分。

结果处理需要单独设计

默认结果保存往往面向任务调试，不一定适合业务数据结构。我当时需要把结构化结果拆成不同字段，因此增加了结果处理层。

可以把这层理解成一个明确的接口：输入是已解析的记录，输出是经过校验和去重的数据。把采集逻辑与数据库逻辑分开，后面修改表结构、增加字段或者重跑任务都会更容易。

选型留下的经验

一个框架是否好用，不只取决于功能清单，还取决于出问题时能否看清它正在做什么。对初学者而言，清晰的组件边界、可复现的单任务调试和完整的失败信息，往往能节省最多时间。

参考项目：pyspider、Scrapy。
