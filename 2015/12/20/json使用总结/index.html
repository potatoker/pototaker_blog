做一个数据采集与展示的小实验时，我第一次完整走过了这样一条链路：

几种语言各有自己的对象、列表和字符串。JSON 的作用，是在这些不同的表示之间约定一种共同的数据格式。这篇记录整理了当时最容易混淆的几个边界。

先分清对象与字符串

Python 的字典、Java 的 JSONObject 和网络上传输的字节并不是同一种东西。序列化将结构转换成文本，反序列化再把文本还原成结构。

调试时看到一段长得像数组的字符串，并不意味着它已经是数组。最可靠的方法是检查类型，而不是看日志的外观。

数据库边界：决定存结构还是存文本

关系数据库中的文本字段只能直接保存文本。如果把列表放进去，需要先进行 JSON 编码；支持 JSON 类型的数据库也可以使用对应的原生字段。无论采用哪一种方式，读写双方都应明确约定。

客户端边界：按约定的类型读取

客户端返回列表时，同样应把列表作为数组放进请求对象，统一编码整个对象。只有接口明确要求“某个字段是一段 JSON 文本”时，才对这个字段单独调用 toString()。

一次排查只看一个边界

我当时遇到的典型问题，是数组入库后变成了字面量 Array。原因不是 JSON 本身丢失了信息，而是某一层把数组隐式转换成了普通字符串。

可以依次检查数据库原值、服务端解码后的类型、HTTP 响应以及客户端读出的类型。每经过一次边界，都确认编码发生了几次，以及下一层期待什么类型。这个办法比在整条链路上反复修改代码有效得多。
