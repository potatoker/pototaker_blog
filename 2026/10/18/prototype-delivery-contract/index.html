把快速迭代的原型，交付成一份能检查、能同步、能验收、会随代码变化而失效的生产契约。

最短理解：把 Warrant skills 装给 AI Coding Agent，然后告诉它你在做「首次梳理、发版、
生产对照还是增量同步」。

日常操作以对 Agent 说话为主——不必在 Terminal 和 Agent 之间来回切换。

Agent 负责读代码、追问和编排；Warrant CLI 由 Agent 代跑，只在你想自己核对参数时才需要看
终端指令参考。

这到底是什么？

Warrant 仓库 vs 宿主仓库

  • Warrant 仓库是工具自身，也就是你正在看的这个仓库。它提供 CLI 和 warrant-* skills。
  • 宿主仓库是 Warrant 正在处理的业务项目。原型项目和生产项目分别是原型宿主、生产宿主；
    .warrant/ 永远放在原型宿主根目录。

两者的关系由运行时的当前目录或 --root 决定，与工具装在哪无关：Warrant 不会因为被
克隆或作为 submodule 加进某个仓库，就把那个仓库当成宿主。因此一份 Warrant 安装可以同时
服务多个宿主项目——CLI 全局共享，每个宿主的 skills 各自从 技能市场安装（见 §1）。

这份本机上下文无法跨仓库交接，所以每个导出的 bundle 都携带原型宿主的 Git 仓库地址、
分支和精确 commit，部署侧据此取得参考源码。其中只有 commit 是必需的——发版钉的是它。

流程长什么样

核心规则：声明随对象指纹失效

Warrant 的核心规则只有一条：

每一条重要声明，都由其所声明对象的指纹作为键。

对象一旦变化，旧声明就不再覆盖它；系统要求重新判断，而不是继续展示一句过期的话。

这条规则有三个主要落点：

声明 存放位置 失效依据
“我们因为这个原因选择了这个值” decisions[].rationale rationale_covers 不再等于当前值对
“这段方案已经由某人确认” confirmations.yaml 方案文字的设计指纹发生变化
“这条必需边已经得到证明” corpus 覆盖索引 用例自身声明的 proves 与登记义务不一致
“生产持有的这份内容和我们一致” materials[] + bundle 里的逐字副本 内容 hash 变化（并因此推动 content_hash）

代码指针、连线、分支和 prompt 等结构变化本身就会触发门禁，因此不要求额外写一段容易过期的解释。只有那些接手方能够改变、而其他门禁又无法发现的选择，才必须留下理由。

谁做什么

Warrant 刻意把判断与计算分开：

工作 由谁完成 原因
找到真正发版 slice、理解变化、追问设计理由 AI skills + 人 这是语义判断，不能由路径 glob 或 AST 代替
字符串相等、集合覆盖、代码符号解析、Git 状态、证据求交 Python gates 门禁必须稳定、可复现，不能被“说服”放行

最关键的门禁包括：

  • 理由自失效：配置值变化后，旧理由不再算数。
  • 证据签收：只接受真实 case 运行证据，不接受手填通过。
  • 内容相等：verbatim 内容资产必须逐字进 bundle，生产侧的副本由 verify-material 做内容比对，不靠肉眼判断「看着差不多」。
  • 双向证明覆盖：覆盖索引和用例的 proves 必须彼此一致。
  • 代码指针解析：file.py::symbol 被重命名或删除时立即失败。
  • 语义流完整性：路由必须有真实分叉，生成器必须声明输入输出，安全门必须画出放行和短路路径。
  • 覆盖率棘轮：只阻断本次新增的孤儿文件，不让历史欠账导致门禁第一天就被关闭。

Warning 永远不阻断。一个会因为既有欠账而天天红的门禁，最终只会被团队禁用。

§1 安装、升级与多宿主

§1.1 首次安装

见 30 秒开始 / 1. 安装 warrant。

安装完成后：

  • 工具源码（$WARRANT_HOME）必须放在宿主仓库之外；不要 git clone 到宿主根目录或子目录。
  • CLI 从 $WARRANT_HOME 安装；skills 默认从 技能市场安装（搜索 warrant 安装全部 warrant-*），
    访问不到 技能市场 的环境才从克隆里手动拷贝兜底。
  • 宿主仓库里只该出现 agent skills 目录下的 warrant-*，以及之后产出的 .warrant/、release
    bundle 和业务改动。
  • 之后 Agent 始终在宿主根目录运行 warrant（或显式 warrant --root "$HOST" ...），不要在
    Warrant 仓库里对另一个项目做 onboard。
  • 只有需要把工具版本钉在宿主里时才改用 submodule（git submodule add <上述地址> tools/warrant）
    ——那是显式例外，tools/warrant 同样不得进入发版 slice。

§1.2 一份安装，多个宿主

Warrant 只需安装一次，即可服务任意多个宿主项目。 宿主身份由运行时的当前目录（或 --root）
决定，与工具装在哪无关，所以多个宿主共用同一份 CLI，不需要也不应该各自再克隆一份工具。

每接入一个新宿主，在新宿主根目录打开 Agent，整段复制：

没有 技能安装工具（或访问不到 技能市场）时改用这段：

由此而来的分工是：CLI 全局共享一份，skills 每个宿主各装一份，.warrant/ 每个宿主各自独立
（onboard 后在各自宿主根目录生成，互不影响）。注意 skills 装完不会自己更新：以后升级 warrant
（§1.3）时，每个宿主的 skills 都要更新一遍，漏掉的宿主会出现「Agent 拿旧说明书开新工具」。
建议记下绑定过哪些宿主，升级时逐个更新。

§1.3 升级到新版本

升级是三样东西要对齐，不是一件事。 CLI 源码（git pull）、已安装的包（pip install -e）、
以及宿主里的 warrant-* skills——最后这个装在宿主的 agent 环境里，不会跟着 git pull 动。
漏掉它的后果不是「没升级」而是「Agent 拿旧说明书开新工具」：旧版 warrant-release skill
会让 Agent 在 export 前先跑 check --require-mainline，于是你在 feature 分支上被拦下来，
而新版 CLI 早就不要求主干。

warrant --version 打印的是运行中的那份代码：版本号 + checkout 的 commit + 目录。
-e 装法下 git pull 之后代码立刻生效但 pip 记的版本号不会动，两者对不上时它会直接
提示你要不要重装——所以 pull 完再跑一次，commit 变了就是升级到位了。

已有的 .warrant/ 与已导出的 bundle 不受升级影响：bundle 是自包含快照，content_hash
按内容算而不按工具版本算，所以升级不会让旧版本对不上。但新版可能新增门禁，于是
warrant check 在你没改任何东西的情况下开始报新的 ERROR——那是新检查在说话，不是升级
坏了，按提示补齐即可。

§2 原型侧：第一次 onboard

在原型项目根目录：

Agent 只冷问两件事：这次想看懂的核心链路是什么（明确说准备发版时才改问
“这次准备交付的核心链路是什么”）、它的输入和输出是什么。之后它必须先去读代码，
再拿分析结果回来动态追问：入口、编排方、不进版范围、
生产开关、动态参数、外部依赖身份、关键配置资产都由它自己算出候选，你只需要挑选或纠正。

它会自动盘点固定资产：用户可见文案、prompt、配置/静态表、资源图、模板和固定
API/URL 默认作为 replication: verbatim，一次列出请你校正遗漏、误收或例外，
不会每份都问一遍「改一行会不会变」。只有 fixture、缓存、派生产物等真无法判断
是否需要完全等量迁移的项，才单独请你裁定。

固定内容如果散落在 Kotlin/Java/Swift/TypeScript 等大逻辑文件里，Agent 直接在
.warrant/materials/ 生成带来源指纹的资产快照。宿主工程保持原样；Python 符号抽取只是
一个便利适配器，不是 Warrant 能否记录资产的边界。

所以它不该给你一份问卷，不该让你列举不进版目录，不该冷问「历史上有哪些坑」——
开放性问题只允许出现一次，在收口时问你还有什么要补充。它也不应该让你手写 schema，
更不应该凭代码猜「为什么这样设计」。

onboard 会在 .warrant/ 通过检查后自动进入图解技术方案生成和浏览器证据捕获，不需要你再补一句
“生成网页”。如果只想单独查看尚未闭合的问题，可以继续说：

人裁的是分析过程中卡住的疑问（证据打架、逻辑说不通），不是把方案层摊开盖章。
一次只问一个疑问；答完由 Agent 写回 artifact / open_questions[]。confirm 是可选的
事后签核，不是 onboard 访谈目标。

文档里这两件事分开渲染，不要混读：

标记 含义 出现位置
待定夺 真的还没有人拍板（未回答的 open_questions[]） 模块页 [!WARNING] + 总览「待定夺」
方案层未签核 已经定了、由代码起草，只是还没人署名 模块页 [!NOTE] + 总览「方案层签核状态」
草稿，未发版 这一页渲染自工作区，其 content_hash 不对应任何 bundle 每页 [!CAUTION] + 页首「渲染自」

前两个说的是内容里还有什么没定，第三个说的是这一页本身能不能交出去。

细则：skills/warrant-onboard/references/interview-design.md、
skills/warrant-onboard/references/interview-decisions.md。

onboard 的主要结果位于：

  • ERROR 会阻断：例如代码指针失效、图的端点不存在、必需分支没有用例。
  • WARNING 不阻断：例如方案尚未由人确认、历史欠账仍在、问题已有记录但未回答。
  • 不要为了清零 warning 让 AI 编造理由。

其中 RELEASE_TREE_DIRTY 值得当场处理：它列出 .warrant/ 之外还没提交的文件，提前
告诉你「照现在这样 export 会被拦下来」。发版钉的是一个 commit，没提交的代码就不在
这一版里——与其等到最后 export 报错，不如现在决定它该不该进这次发版。.warrant/
自己不算在内，那是本轮产出，随流程一起提交。

§3 原型侧：发版

export 会：

  1. 再次执行门禁（含 import 闭包审计：已注册源码的 import 链路上的活文件必须
    注册进 nodes[].sources 或带理由地豁免，否则 SOURCE_CLOSURE_UNDECLARED 阻断）；
  2. 计算并写入 content_hash；
  3. 生成 release-manifest.yaml，写入原型仓库地址、当前分支和精确 commit；
  4. 导出部署侧可以独立读取的 bundle，并标配生成 SYNC_CHEATSHEET.md——
    与上一版 bundle 的 diff 渲染成的部署行动清单（必须重拷 / 必须读实现 /
    必须确认取值 / 必须回答的开放问题，标注本版新增 vs 历史携带 / 验收命令）；
  5. 拒绝非 Git 宿主、无 commit 的仓库、脏工作树，以及接手方无法定位源码的版本。

发版对分支没有要求。 一次发版钉的是 commit，不是分支：feature 分支、自定义主干、
detached HEAD 都可以发，也不需要先合入 master。唯一的 Git 要求是宿主代码已提交——
工作树是脏的，manifest 里那个 hash 就描述不了真正发出去的代码。这条不该留到 export
才发现：warrant check 一路上都会用 RELEASE_TREE_DIRTY 报出来，skill 也会在开工前先问一句。

commit 尚未推到任何远端分支时 export 照常成功，但会警告 RELEASE_COMMIT_UNPUBLISHED：
bundle 本身完整，只是在推之前部署侧 fetch 不到 manifest 指的那个 commit。export 自己写进
.warrant/releases/ 的产物不算脏，所以连发两次不会被自己挡住。

团队若确实要求「每个 bundle 都出自主干」，那道检查仍在，改为显式开启：

不传 --out 时，bundle 默认写入宿主项目的：

这是宿主项目的一部分，应随本次宿主 Git 发版 commit 一起提交。部署侧 checkout 该宿主
commit 后即可直接读取 bundle，不需要再从 Warrant 工具仓库寻找产物。如果使用显式 --out，
请仍然选择宿主仓库内、未被 .gitignore 忽略的目录；Warrant 不会替你执行 git add 或 git commit。

发版不是「把当前目录压缩一下」。它交付的是一版明确的行为声明，以及证明这些声明所需的用例。

技术方案文档是这版声明的视图，不是另一份平行文档，所以它读 bundle：页首写明发版
content_hash 和原型 commit，内容资产展开的是 bundle 里 materials/ 的逐字副本，而不是
「渲染那一刻工作区里恰好是什么」。不加 --bundle 渲染出来的页面会自己标成草稿——那是自查
用的，别发出去。

部署侧跟新版

changes.json 说明哪些行为契约和源码指纹发生了变化，原型 Git 历史则解释这些变化在

attribute 不会用路径规则猜变化属于谁；归属由能理解改动的人或 Agent 判断，CLI 只保证没有遗漏。select 负责检查所选单元是否依赖闭合。

§6 承认差异：只同步一个单元

现实里两侧往往已经存在历史差异，而你暂时不打算统一整条链路——只想把某一个具体逻辑（示例：example_unit）迁过去。这正是 sync unit 的用途：差异保持原样，迁移按单元发生。

原型侧（一次性）：把这个逻辑声明为 sync unit

这是一次性动作。之后每次发版照常（§5），不需要再提 slice；bundle 照常随仓库提交在 .warrant/releases/ 下。

部署侧（一次性，仅未装过 warrant 时）：安装

「安装到你自己使用的 skills 目录」是有意这么写的：skill 目录因 Agent 而异（Kimi Code 是 .agents/skills/，别的 Agent 另有自己的约定），Agent 自己最清楚它从哪里加载 skill。能从 技能市场装的话，也可以改用 warrant-install skill 走市场渠道。

部署侧（每次跟随时）：只取这个单元

部署侧不需要任何人递路径或 hash：Agent 会自己从原型仓库的 .warrant/releases/ 定位最新 bundle，选择 example_unit（依赖自动闭包），用 warrant slice 切出只含该单元的迁移包，照着包实施，并对切片后的 corpus 跑 verify。它不会签完整 content_hash——那是整版的指纹，部分同步签了就是以偏概全。

如果 Agent 报告 example_unit 依赖了另一个单元而要求一并带上，那不是它在加戏：依赖闭包保证你拿到的组合是原型侧真正测过、描述过的组合。如果你确认只要 example_unit 本身，那就回到原型侧，把耦合拆开再发版。

Warrant 不做什么

  • 不替人决定发什么。 slice 必须由项目负责人确认。
  • 不从代码推断设计动机。 找不到理由就提问或留空，不生成合理化解释。
  • 不要求生产复制原型源码。 交付的是行为契约和证据，不是目录结构。唯一例外是
    materials[] 里声明 replication: verbatim 的内容资产——prompt、风格池、模版
    这类东西没有「等价重写」，只能整份搬过去。
  • 不把原型源码当成隐含上下文。 audit/sync 必须按 bundle 定位并验证原型 Git commit。
  • 不自动编写领域结果提取器。 如何把运行输出映射成 case 结果属于宿主领域。
  • 不把实现细节塞满技术文档。 代码和 schema 只有被 evidence[] 声明为关键证据时才折叠展示。
    被 materials[] 声明的内容资产是另一回事：它是产品表现的来源，紧跟「方案」单列一节，
    给摘要行 + 可扫索引表 + 折叠全文。
  • 不替人签核。 confirm 必须由真正读过方案的人确认后执行；Agent 不得自行署名。
  • 没有接手方时价值有限。 它保护的是一次跨责任域交接。
