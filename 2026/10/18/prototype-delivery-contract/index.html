从某 AI 原型项目的一次交接，到一套给人和 AI 共同使用的 production artifact

Vibe Coding 最爽的一刻，是你用几句话让一个想法真的跑了起来。

最尴尬的一刻，是另一个人接过仓库，问：

“所以，这套东西到底是怎么跑的？”

我们在把某 AI 原型项目推向正式上线时，正面撞上了这个问题。

这是一个典型的小团队快跑项目。三个人包揽产品与开发，通过 Vibe Coding 快速试想法、改效果；原型跑通以后，再由专门的线上团队完成生产实现：

仓库当然可以直接交过去，但它没有标明哪条链路属于正式版本、哪些 prompt 和配置必须上线、哪些文件只是历史实验，也没有提供跨实现验收的方法。

原型转向生产时，这些问题一起冒了出来，也暴露出真正的缺口：

代码留下来了，产生这些代码的上下文却没有。

这篇文章讲的，就是我后来怎样沿着代码，把那份消失的上下文一点点找回来。先剧透一下最后得到的东西：

一份与代码配套的规范。人可以用它理解和查证，AI 可以用它继续开发和迁移，程序可以用它验收。

它不是“让 AI 帮我补一篇文档”，更像是把代码重新编译成了另一种生产产物。

01｜问题：代码留下来了，上下文去哪了？

一个自然的解法：让所有人只改同一份 spec

这里说的 spec，是一份给人和 AI 共同使用的结构化说明：它写清软件应该怎样表现、必须遵守哪些约束，以及怎样才算做对。

既然上下文会消失，一个自然的解法就是不再让它散落在对话里：给项目维护一份长期存在的需求文档或技术 spec。

以后每冒出一个想法，都先修改这份文档；AI 每次开始工作，也先读取它，再按照最新描述实现需求。

这就是 Spec-Driven Development（SDD）最直观的出发点：让 spec 接住原本会从对话中消失的上下文，并成为人与 AI 共同工作的稳定起点。

但两句话就能试出来，谁还会先改文档？

一个想法明明用两句话就能让 AI 先做出来，你真的会停下来，对着那份漂亮的文档字斟句酌，把相关章节全部更新准确以后，再允许 AI 动手吗？

但在真实的原型开发里，大多数人仍然会选择想法先行、尝试先行：脑子里刚冒出一个想法，先告诉 AI；几分钟后页面能点、流程能跑、内容已经生成了；看完效果，马上又开始下一轮。

这条闭环里，代码和效果出现得太容易，文档却不参与下一次尝试，也不阻止下一次修改。它通常要到汇报、交接或评审时，才被“漂漂亮亮地生成一份”。

只要后续迭代可以一直绕过它发生，它就不是“有可能”过期，而是必然会 rot。

有一句话可以概括：

没有进入下一轮反馈的东西，就不会跟着下一轮一起演化。

这不是 SDD 对不对的问题，而是 Vibe Coding 的真实发生顺序已经改变：先围绕效果反复尝试，需要交付时才重新想起文档。

等我意识到缺少 spec 时，实现早已长出来。此时更诚实的起点，不是从头描述一个“看起来应该如此”的理想系统。

应该先沿现有代码恢复实际发生了什么，再通过规范化问答补回代码里没有的意图，最终形成可执行规约。

对我们的原型项目来说，这个“需要交付”的时刻来得很具体：另一支团队要在自己的生产集群、模型服务和工程约束下，把已经跑通的原型正式上线。

于是问题从“怎么补一份 spec”，变成了：

我到底应该把什么交给部署团队和他们的 AI？

原型交给线上时，究竟要还原什么？

原型侧已经亲自运行、体验过，并确认“这一版效果对了”；线上侧要做的，是在自己的模型服务、工程框架和生产环境里让同样的效果重新成立。这一步表面上在交接代码，实际交接的是责任：

原型侧交付“这版效果已经成立”；线上侧接手“怎样让它在另一套生产实现里继续成立”。

如果双方使用完全相同的代码和环境，这件事可能只是一次部署。只要线上项目需要换语言、框架、模型服务，或者重新接入安全、监控和降级链路，“把仓库发过去”就不再等于完成交付。

线上项目真正需要还原的是：

要对齐的对象 线上侧必须弄清楚
正式范围 本次交付的行为主线是什么
效果来源 哪些实现和配置共同产生了已验收效果
不变量 哪些约束必须保留，哪些实现细节可以替换
排除项 哪些文件只是历史、实验或临时排查
验收方法 新实现怎样独立证明效果已经还原

因此，一次能够被线上真正接住的交付，不能只有一份仓库，至少还要带上三样东西：

  • 参考实现：已经验收的效果，具体由哪一版代码和配置产生；
  • 生产规约：换一种技术实现以后，哪些行为与约束仍然必须成立；
  • 验收证据：线上项目用什么输入、输出和判断标准，证明自己真的还原成功。

三者还必须绑定在同一个版本上。代码来自今天、说明来自上个月、验收样例来自更早以前，拼在一起无法代表任何一版真实产品。

其中最容易缺失的是生产规约。PRD 描述希望用户获得什么体验，原型代码展示当前实现怎样产生这个效果，而生产规约要回答：

无论最终使用什么语言和框架，哪些行为与约束都必须成立，以及怎样才算还原成功。

我把这层信息叫作生产技术规约。它不是在 PRD 和代码之外再堆一篇文档，而是原型实现与线上实现共同遵守的协议。

代码是一种参考实现；规约定义另一份实现必须保留什么；证据负责判断它是否真的保留了。

代码装下了实现细节，却不是最高层上下文

真正棘手的是，生产技术规约不能直接等于一份“代码说明书”。

代码仓库是项目信息最多的地方，却不一定是项目上下文最完整的地方。

正式链路、临时补丁、被放弃的方案、实验入口和三个月前的默认值，都以同样的“代码文件”形态留在那里。

仓库保存了它们，却没有自动标出它们在产品里的权威等级。

如果把产品开发看成一条编译链，这个包含万象的代码仓库，很像一份已经展开到实现层的中间产物：

走到代码这一层，大量实现细节被保留下来，最上游的结构却被压平了。

AI 可以解释每个函数，但仅凭这些函数，它仍然要猜：

  • 正式主线｜ 哪些代码共同构成真正的产品行为；
  • 必要约束｜ 哪些选择必须被下一份实现保留；
  • 偶然实现｜ 哪些细节只与当前语言和框架有关；
  • 历史遗迹｜ 哪些代码虽然还在仓库里，却已不代表产品。

所以 AI 需要的不是比仓库更多的信息，而是比仓库更高一层的权威上下文。

这时，一个更大的问题自然出现了：

如果代码只是已经展开到实现层的产物，那么 AI 时代，一个项目真正的“源码”是什么？

它至少应该包含正式范围、行为模型、关键约束、决策理由，以及判断还原是否成功的证据。

这里的“源码”不是要替代代码：代码仍然负责重现当前构建，这层上游上下文则负责让另一位人或 AI 重现项目真正想保持的行为。

但一份不参与交付的规约，也只是一篇漂亮文档

答案看起来很简单：补一份完整、专业的技术规约。但它马上会遇到一个更现实的问题——谁会一直更新它？

只要代码可以在规约未更新时继续开发、验收和上线，无论它第一次写得多完整，最终都会过期。这不是责任心问题，而是更新规约并非下一步的硬依赖。

一旦赶进度、切换会话或更换负责人，它就会从“共同协议”退化成参考材料。更危险的是，它仍然写得很专业，下一位人或 AI 很可能继续把它当成事实。

因此，本文并不把一致性寄托在“大家记得维护文档”上，而是依靠两个强制动作：

一致性发生在什么时候 使用什么机制 它解决什么问题
第一次形成规约 从正式代码入口反推阶段、数据流、配置和源码指针，再让人只补代码无法回答的意图 让规约描述“当前实际上怎样”，而不是重新想象一个理想系统
以后每次发版 强制重新同步规约、证据和版本身份，并由 gate 检查指纹、覆盖关系与内容哈希 代码一旦变化，旧规约就不能继续冒充当前版本完成交付

这里的“强一致性”并不是要求每次 Vibe Coding 都实时改一篇文档。日常探索仍然可以很快；但到了发版边界，参考实现、规约、验收证据和版本身份必须形成同一份一致快照。只改代码而没有同步其他部分，这一版就不能被声明为可交付。

所以，“技术文档”和“生产规约”真正的区别，不在于谁写得更详细：

只靠自觉维护的文档 真正进入交付流程的规约
代码变了，文档可以不变 规约、证据或版本不一致时，交付会失败
读者只能相信作者写得对 重要声明可以回到代码、决策或测试查证
过期以后安静地留在那里 对象变化后，旧声明会主动失效
主要供人阅读 同时是人、AI 和程序的输入

换句话说：

一份文档不是因为名字叫“规约”就有约束力。只有当违背它会产生可见后果，它才真正成为交付物。

这也反过来规定了我要做的东西：

设计要求 必须做到
事实优先 从当前代码恢复事实，而不是从作者心里的理想系统开始
意图不猜 代码答不了的问题，必须通过规范化问答交还给人
结果可验 不只生成 Markdown，还要携带可执行的验收证据
过期可见 与代码、版本及发布流程绑定，失效时能够阻断或报警

后面会反复出现几个工程词，先把它们翻译成直白的话：

文中术语 可以先理解成
slice 这次真正要交付的一条正式功能路径
source pointer 一条声明具体来自哪个文件、函数或配置
golden case 一组固定输入，以及它必须触发的关键行为
fingerprint / content hash 给局部声明或整份交付物按下的“内容指纹”
gate 不听 AI 解释、只按规则和证据放行的检查
waiver 已经知道、暂时接受，但不能假装不存在的缺口

这些看起来有些“重”的设计，其实都在回答同一个问题：

怎样让这份规约不只靠人的意志，也能留在真实交付路径里？

规约怎样进入流程？把“发版”定义成交付

这里不是要让开发者每和 AI 对话一次，就停下来维护一篇巨大的技术文档，那样只会拖慢 Vibe Coding 最有价值的反馈速度。真正适合建立硬边界的动作，是发版。

在原型侧，日常迭代仍然可以很自由：

但当负责人说“这一版可以交给线上”时，含义就应当发生变化：它不再只是“把当前代码提交一下”，而是在声明：

这份实现、它对应的上下文，以及证明它成立的证据，共同构成一个可以交付的版本。

所以在原型 → 线上的模式里，需要重新定义 release：传统发版关注代码和构建产物；AI 原型的生产发版还必须带上规约、验收证据与精确版本身份。

其中，“代表这一版实现的上下文”是最关键的部分。它不是原作者所有聊天记录的归档，也不是一篇与代码各自演化的说明文档，而是与这个版本绑定的最小上下文：

发版内容 它回答什么
Reference implementation 这一版真实跑通的代码和正式入口在哪里
Production spec / context 正式范围、技术行为、配置与关键决策是什么
Acceptance evidence 哪些 case 已经证明这些行为成立，哪些缺口仍被 waiver
Version identity 它对应哪个 commit、内容哈希和环境基线
Change set 相比上一个可交付版本，究竟改变了什么

发版动作负责选择正式 slice、恢复规约、补充代码答不了的 why、运行 proof / golden / gate，最后导出带 content_hash 的不可变交付包。

任何一项关键内容缺失，发版就应该失败，或者至少明确带着 waiver 发出。这样，规约才不再依赖开发者“记得更新”，而会成为发布版本时必须生成、检查和消费的东西。

生产侧接收的也不再是一个仍在继续实验的仓库，而是一个已经定版、能够被解释和验证的 release。

这也是我理解的 AI 时代 production artifact：

它不是代码旁边多放的一份文档，而是一次发版本身必须携带的、能够解释并验证这个版本的上下文。

把几个容易混在一起的词放在这里，它们其实是三层关系：

本文使用的概念 它指什么
生产技术规约 这份上下文的核心：范围、行为、约束、决策与验收义务
Production artifact 规约与参考实现、证据、版本信息一起进入发版后的交付形态
AI 时代的“源码” 足以让下一位人或 AI 重建目标行为并判断成功的最小可重现闭包

下一次原型发版时，不必让生产侧重新阅读全部历史。新 release 只需携带版本身份、当前规约、对应证据，以及相对上一版的结构化 diff。

到这里，问题终于从“缺一份文档”，收敛成了“怎样从现有仓库可靠地生产这套交付物”。

02｜实践：怎样从代码恢复一份可验收的规约？

直接把整个仓库交给 AI，不行吗？

我最早确实想过直接让 AI 读完整个仓库。它解释单个函数、整理一组文件的模块关系都很快，但“读得懂代码”和“知道该交付什么”是两件事。

原型项目的仓库里同时存在：

仓库里能看到的东西 部署时应该怎样理解
正式链路 必须实现
旧版链路 可能只是历史参考
实验 prompt 不能因为文件还在就带进生产
测评入口 用来验证，不一定属于线上调用链
临时排查代码 更不应该成为产品能力
代码默认值 不一定等于生产部署值

这时让 AI “总结一下仓库”，很容易得到一篇流畅、完整，却把实验代码也纳入正式范围的文档。

AI 有一种危险的体贴：碰到空白时，它会努力给出一个听起来合理的解释。人面对不确定的代码往往会停下来问，AI 却更容易继续向前，把推断写成事实。

所以我后来不再问：

帮我总结这个项目。

而是改问：

本次需要进入生产环境的，究竟是哪条从输入到输出的完整功能链路？

第一次转折：从“总结仓库”变成“追踪入口”

第二次转折：这份规范不只是给人看的

一开始，我把 manifest 和配套说明理解成“部署文档”，后来才发现，它甚至更适合给 AI 看。

人的阅读习惯和 AI 不完全一样：

同一件事 人更需要 AI 更需要
系统范围 一张图、简短说明 稳定 ID、结构化 schema
技术声明 原因、背景、可读文字 精确字段、枚举值、依赖关系
查证 file.py::symbol 源码指针 可解析 pointer、fingerprint
版本变化 “这次为什么改” 前后 artifact 的结构化 diff
验收 能看懂的结果 case、obligation、evidence

这不意味着要维护两份规范。更好的方式是维护同一组结构化事实，再生成不同视图：

  • 给人的版本：技术文档、流程图、决策说明；
  • 给 AI 的版本：manifest、变更包、源码指针、约束；
  • 给程序的版本：golden case、覆盖关系和 gate。

这时，技术文档不再是独立维护的附属品，而成为 production artifact 面向人的视图：原型侧 AI 从代码与问答生产 artifact，人通过文档理解和查证，生产侧 AI 消费结构化版本完成实现，程序再依据同一组 case 验收。

对我来说，这是整件事里最抓人的变化：

过去文档主要解决“人和人怎么对齐”；现在它还要解决“AI 和 AI 怎么对齐”。

只有说明还不够：还要有一套验收 CI

如果部署侧实现完成后，仍然只能由人上线点一遍功能，这件事就只做了一半。页面最终“能生成内容”，不代表多阶段 AI 链路里的每个行为都正确：

验收层面 需要检查
安全前置 对话是否脱敏，命中风险后是否及时阻断
路由行为 S3 是否选择了正确的生成路径
数据交接 上一阶段字段是否完整传给下一阶段
生产配置 环境开关是否固定在正确取值
异常策略 fallback 是否真的实现，而非碰巧没有报错

所以 manifest 之后，我们又补了三样东西：

产物 回答的问题
manifest 本版本完整要实现什么
golden corpus 哪些输入应该触发哪些关键行为
deploy packet 相对上次同步，这次究竟改了什么
content_hash 生产侧现在对齐的是不是同一版内容

这里的“验收 CI”，不是泛指代码能不能编译、单元测试是否通过，而是原型实现与生产实现之间的独立裁判。它要回答的是：

生产侧换了一套实现以后，有没有把本版本规定的正式行为真正还原出来？

生产侧 AI 先读取 deploy packet 完成本次变化，再用生产实现运行同一组 golden case；验收 CI 根据实际 evidence 重新计算 PASS / FAIL——登记一个 case 只代表“它应该证明什么”，不能代替生产实现真正跑出的证据，暂时无法证明的内容则明确标为 waiver。

03｜业界：Vibe Coding 之后，软件开发在往哪里走？

做到这里，我才开始认真查找：这件事在业界到底叫什么，别人又在怎样解决？

“原型已经跑通，但不知道怎样变成可维护产品”还没有统一名字。

prototype-to-production gap、vibe coding to production、codebase cognitive debt 等不同说法，都在汇向同一个问题：

当 AI 把实现变得非常便宜，过去用来保存意图、形成共识和定义正确性的那些工件，还剩下什么？

原型项目只是把这个变化放大了。对于普通项目，它可能表现得更日常：

你看到的现象 背后的上下文缺口
三个月后自己已经看不懂 项目脉络只存在于当时的记忆
新 AI 会话反复重读仓库 没有稳定、可继承的上层上下文
新功能悄悄破坏旧功能 重要行为没有成为可执行约束
文档很多，却不知道哪份是真的 文档没有版本身份与失效机制
agent 说“已完成”，人仍要亲自点一遍 实现者的声明没有独立证据

问题的尺度不同，根因其实很接近。

Vibe Coding 改变的，不只是写代码的方式

“用自然语言生成代码”只是最表面的一层，更深的变化发生在产品开发的组织结构。传统开发不只是“产品写需求、开发写代码”，而是一条把产品意图逐层收敛成运行实现的链路：

这条链不能保证软件永远正确，却会在每一次开放判断之间，留下下一棒必须消费和检查的工件：

交接阶段 必须消费和检查的工件
产品 → 开发 需求文档：确认“要做什么”
开发 → 开发 技术方案：确认“准备怎样做”
开发 → 构建 code review、测试和 CI：检查源代码
源码 → 制品 编译器与构建系统：完成确定性转换
制品 → 运行 发布与运行系统：验证目标环境中的行为

这些文档和代码都在充当 boundary object——跨角色边界的共识对象。

  • 产品 → 开发｜ “要做什么”必须通过需求文档交接；
  • 开发 → 开发｜ “准备怎样做”必须通过技术方案评审；
  • 代码 → 运行｜ 实现必须经过 review、构建、测试与发布。

它们长期存在，不只是因为流程要求，而是因为没有这些工件，下一棒的人就无法开工。

AI 出现以后，这条链并未失效。SDD 仍然保留“意图 → spec → 实现 → 构建 → 运行”的顺序，只是让 AI 承担更多技术翻译和 Coding。

真实的 Vibe Coding 却常常走一条更短的路：产品、设计和开发角色开始重叠，人直接根据运行效果给 AI 下一轮反馈。

同一个人提出想法、让 AI 修改、自己运行，再立刻决定下一步。产品、设计和开发没有消失，却不再总是由三个角色依次完成。更准确地说：

开发从“以角色交接为中心的串行流程”，变成了“以运行结果为中心的人—AI 高频反馈闭环”。

传统产品开发 Vibe Coding 式原型开发
产品提出需求，开发负责实现 产品、设计、开发常常变成同一个人和 AI 的组合
需求必须先被写下来，才能跨角色沟通 直接把想法告诉 AI，马上就能看到能跑的东西
PRD、技术方案是下一角色开工的硬依赖 角色边界变模糊，文档变成旁路工作
原型通常是一次性验证品 原型经常直接长成真实产品
代码是实现结果 代码逐渐变成唯一留下来的行为记录

意图抵达实现的保证并没有消失，只是被推迟到了下一次责任边界。

要理解为什么原型发版必须补回 production artifact，还要再看一件事：Vibe Coding 过程中，人究竟在验收什么？

新范式里，真正被验收的交付物是“效果”

角色边界被压缩以后，“什么东西会被认真检查”也随之改变。传统开发的下一棒真的在等待需求单和技术方案；Vibe Coding 里，同一个人直接和 AI 对话，最后检查的是：

看什么 实际验收的问题
页面 是不是我想要的样子
流程 能不能真正跑通
内容 生成内容的效果对不对
迭代 这次修改有没有改善体验

换句话说：

Vibe Coding 的真实交付物不是需求单，不是技术方案，甚至不一定是人能解释清楚的代码；它首先是效果。

只要效果通过，人通常不会再逐项检查 AI 补了哪些假设、选择了哪种结构、遗漏了哪些边界。于是一个典型的 Vibe Coding 项目会留下这样的结果：

效果被验收，代码被保存，上下文被丢失。

这也解释了为什么预先写好的文档容易过期。它可能结构完整、措辞专业，但后续迭代已经只围绕效果进行。

一旦不再被任何角色消费，它就会变成一份漂亮的幻觉：描述了一个逻辑自洽的系统，却不是眼前这个已经跑起来的系统。

有一句规律很朴素：

组织真正检查什么，什么才会留下来。

当原型交给生产团队、另一个开发者或新的 agent 时，角色边界重新出现。此时不必强行恢复过去的文档流程，而要找到新范式真正缺少的交付物：

一份能把已经验收过的“效果”，连接到正式范围、技术行为和可执行证据的生产交接物。

这不是开发者突然不爱写文档，而是成本曲线变了：过去，“把需求讲清楚”和“把功能做出来”之间隔着一个团队；现在，对着 AI 把功能先做出来，可能比把它描述清楚还快。

需求和技术决策并未消失，只是换了一种不稳定的存在方式：

原来显式存在于 现在隐含存在于
PRD 与需求单 对 AI 说过的功能指令
技术方案与评审记录 一连串局部代码修改
设计决策 “这版效果对了”的即时判断
验收标准 作者亲自点击、体验和比较的记忆

但对话会结束，人的记忆会淡，下一位 agent 也拿不到上一轮完整上下文；最终稳定留下来的，通常只有代码。

业界关于 prototype-to-product 的讨论里，有一个很有用的区分：原型是一组“曾经成功运行过的行为”，产品则是一组在持续修改、用户增长、作者睡觉时仍然要保持成立的行为。

两者之间差的不是一次“把代码写专业点”的重构，而是一套让重要行为长期成立的结构。

如果把这两年的发展压缩成一张表，大致可以这样看：

阶段 人主要在做什么 随之暴露的问题
Vibe Coding 用自然语言快速得到可运行结果 代码增长很快，意图和推理留在会话里
AI-assisted / Agentic Engineering 拆任务、调度 agent、让它执行更长流程 agent 缺少稳定上下文、工具和反馈
Spec-Driven Development 把意图提前写成 agent 可消费的 spec spec 的成本、生命周期和已有项目接入成为问题
Reverse Spec + Harness 从已有代码恢复契约，并把验证嵌回 repo 怎样保证声明可信、过期时会失效

这不是四个互相取代的流派，而是同一个过程：每当 AI 接管一层工作，工程问题就向上一层移动；代码生成变便宜以后，新的瓶颈变成了意图、上下文、验证和治理。

回到前面的 SDD：业界把 spec 推到了多远？

Part 01 里，SDD 刚出现就被我追问了一句：一个想法两句话就能先做出来，谁还会停下来维护文档？

现在回头看，这个质疑击中的其实是最朴素的 spec-first：先写一份更完整的任务说明，再让 AI 实现。如果 spec 只是在开发前多出的一篇 Markdown，后续修改又可以绕过它继续发生，它当然会退化成漂亮文档。

但业界对 SDD 的设想比这走得更远。GitHub Spec Kit、Kiro 和 Tessl 都试图把 spec 从一次性任务输入，提升为人和 AI 共同消费的主工件：它不只描述产品目标，还向下延伸到行为、技术设计、任务拆分和验收条件。

GitHub Spec Kit把它描述成一次“权力反转”：过去代码是真相、文档只是建议；SDD 希望 spec 成为主要工件，代码变成它在特定语言和框架下的表达。

目前常见工具的路线很接近：

工具或路线 典型流程
GitHub Spec Kit Specify → Plan → Tasks → Implement
Kiro Specs Requirements → Design → Tasks → Implementation
Tessl 把 spec 推到更接近 source 的位置，由 AI 生成实现

不过，SDD 并不是一种强度固定的做法。

Thoughtworks 的 Birgitta Böckeler 在对 Kiro、Spec Kit 和 Tessl 的比较里，把它分成了三个台阶：

最上层的 spec-first 只是先写 spec，再生成代码；spec-anchored 开始要求后续修改仍围绕同一份 spec 进行；到了最激进的 spec-as-source，含义已经完全不同：

spec 不再是代码旁边的说明文档，而是人真正维护的“源码”；生成代码只是它在某种技术栈下的派生产物，原则上可以丢弃并重新生成。

这条路线解释了为什么 AI 编码工具越来越喜欢生成 requirements.md、design.md 和 tasks.md：大家在重新把“意图”提到代码上游。

所以，前面对 SDD 的质疑需要说得更准确：SDD 不是无效；只有当 spec 真正成为后续变化的硬入口时，它才不会退化成漂亮文档。

这也正是 SDD 与本文场景分叉的地方。SDD 从“先有 spec”出发，我们却是在代码和效果已经长出来后，才发现上游上下文已经消失。把它直接搬进已有原型，仍会遇到几道问题：

问题 为什么会发生
时间线相反 SDD 最顺手的路径是 spec 在前；原型场景是代码和行为已经在前
谁是真相源 新写的 spec 可能描述“理想上应该怎样”，代码则保存“现在实际上怎样”
主链路约束不足 如果改代码可以绕过 spec，它仍然会退化成下一份过期文档
流程可能过重 每个小改动都生成大量 Markdown，会重新拉长刚被 AI 压缩的反馈循环
正确性仍未解决 spec 描述了目标，不等于另一份实现已经提供了满足目标的证据

这些问题并不否定 SDD；它们说明 SDD 更擅长治理“从现在开始的变化”，却不能自动恢复“过去已经丢失的上下文”。只有成为 AI 的输入、CI 的检查对象或发布的必要条件，spec 才真正回到开发主链路。

所以 SDD 回答了一个重要问题：

从现在开始，怎样不再丢失意图？

但对于已经存在的原型，还要先回答另一个问题：

过去已经丢失的意图和行为边界，怎样尽可能诚实地找回来？

SDD 解决正向路径，已有原型需要反向路径

SDD 与已经跑起来的 Vibe Coding 项目，从时间线的两端出发：

这时需要的是反方向。这条路线有时被叫作 reverse SDD、spec recovery、spec extraction，也有人使用 DDS（Development-Driven Spec）。

这些名字目前都还不是稳定的行业术语。

需要反推，不是因为“从头补写一份技术方案”做不到，而是因为此时最可靠的证人已经换了：

  • 人的记忆只能证明当时想过什么；
  • 旧 PRD 只能证明最初计划过什么；
  • 代码、测试和运行结果才证明系统现在真的做什么。

直接凭记忆重新写一份正向 spec，很容易把“今天已经存在的行为”写成“我现在觉得它应该有的行为”。

反推则先承认原型是一份 reference implementation，从正式入口沿真实路径恢复当前契约，再把无法从代码得出的意图交还给人回答。

PAELLADOC 的 repo-to-product-artifacts 方法是我看到目前最接近这个问题的尝试之一。

它把从代码恢复信息分成了三个深度：

反推对象 最主要的证人 可信程度
Stories：系统向用户提供什么行为 route、handler、UI state 较容易恢复
Acceptance criteria：什么条件必须成立 test、validation、error branch 有测试时相对可靠
Decisions：为什么选择这种结构 Git 历史、提交记录、owner 访谈 丢失最多，也最容易被 AI 编造

这也解释了“让 AI 自动生成技术文档”为什么经常看起来很好、实际上不敢用：越靠近 WHAT，代码证据越充分；越靠近 WHY，信息缺失越严重。

如果工具为了文档完整而顺手补齐 WHY，它不是在恢复规范，而是在把猜测洗成事实。

所以反向 SDD 的第一条专业纪律不是“生成得更全”，而是像图中那样保留来源依据（provenance），明确区分 PROVEN、SOURCED、INFERRED 和 UNKNOWN。

空白也是一种有价值的产物，因为它明确告诉下一位人或 AI：这里不能继续猜，需要找谁回答。

反推出来的，不能只是一篇技术文档

这里很容易产生一个误解：

既然要从代码整理技术事实，那最后让 AI 写一篇架构文档不就行了？

架构文档当然有用，但它不是反推流程的核心产物。

真正需要恢复的是一组代码配套规约：

规约里的内容 它回答什么
Scope / slice 这次正式交付哪条路径，明确排除什么
Graph / wiring 有哪些阶段，数据怎样跨阶段流动
Contracts / decisions 哪些配置必须固定，基线值和生产选择是什么，为什么
Source pointers / provenance 每条技术声明从哪里得出，可信等级是什么
Obligations / golden cases 哪些边和行为必须被另一份实现证明
Unknowns / waivers 哪些事实还不知道，哪些缺口暂时接受以及怎样验证
Version / diff 这份规约对应哪一版代码，相比上一版变了什么

它和一般技术文档的区别，可以这样看：

一般技术文档 反推得到的代码配套规约
主要目标 解释系统，帮助人阅读 约束后续实现，并定义怎样算正确
主要形态 Markdown、图和叙述 结构化 artifact + 面向人的渲染视图
与代码关系 文档作者根据理解进行描述 重要声明带源码指针、版本和 provenance
面向未知 往往倾向写成完整叙述 允许 INFERRED、UNKNOWN 和 waiver 显式存在
更新机制 依赖维护者记得同步 对象变化后 fingerprint、pointer 或 gate 让旧声明失效
AI 怎样使用 作为参考上下文阅读 可以解析、diff、选择同步单元并执行验收
能否签收 通常不能，仅提供说明 proof 与 evidence 足够时可以计算 verdict

所以“反推技术文档”这个说法只说对了一半。

更准确的关系是：

技术文档仍然重要，但它应该是同一事实源面向人的 view，而不是另一份需要手工保持同步的真相。

Coding 变便宜以后，什么才是项目真正的“源码”？

前面在原型交接里，我已经抛出了这个问题。走完 SDD 与反向恢复这两条路径后，现在可以更认真地回答它：

过去，Coding 是开发过程中最昂贵的部分之一。需求、设计和技术方案最终都要由人翻译成代码，代码自然成为最值得长期维护的核心资产。

如果 AI 可以低成本地反复生成实现，真正不能丢的就变成了项目上游的四类上下文：

上层上下文 它回答什么
Intent 我们究竟想把它做成什么
Boundary 哪些范围、约束和决策不能重新猜测
Accepted behavior 当前哪些行为已经被接受
Oracle 下一份实现怎样证明自己仍然正确

这里的“最顶层”并非最抽象、最宏大的文档，而是：

一旦丢失，下一位人或 AI 就不得不重新猜测项目意图、实现边界和验收标准的那组最小上下文。

Sean Grove 在《The New Code》里有一个很有冲击力的比喻：

我们写 prompt 让 AI 生成代码，最后只保留代码、丢掉 prompt，就像把源码碎掉，只把编译后的二进制放进版本库。

这个比喻说对了一半，也说错了一半：

判断
说对了 我们丢掉了生成实现时的上游意图，只保留最下游结果
说错了 它容易让人误以为 prompt 是新源码、模型是新编译器、生成代码是新二进制

再往前追一步，prompt 本身并不是那份新的源码。

因为从 prompt 到代码，AI 替我们补了大量没有说出口的东西：

  • 工程选择｜ 具体库、目录、抽象、数据结构和异常处理；
  • 仓库惯例｜ 当前项目已经形成的模式与依赖；
  • 运行条件｜ 当时的模型版本、上下文和工具；
  • 迭代历史｜ 前后几十轮对话里的修正。

同一句 prompt 换一个模型、换一次会话，甚至只换一个已有仓库，都可能得到不同代码。因此，它不是一份充分输入，更像是对一个非确定性开发者下达的任务指令。

回看前面那张传统链路图，其中真正接近确定性转换的是后半段。

需求单和技术方案从来不能精确重现同一份代码，因为人类开发者也会在实现时补足大量细节。

源代码之所以成为那个稳定的 source，是因为它位于最后一次大规模开放判断之后、确定性构建之前。

传统编译链里，“源码”之所以叫源码，是因为在给定依赖、构建配置和工具链以后，它足以重现下游产物。

严格来说，即使在传统时代，只保存 .cpp 或 .ts 也不一定足够；reproducible build 还需要依赖、编译参数和环境。

AI 把“开放判断”这一段也自动化了：

所以今天真正棘手的，不是代码能不能继续编译，而是第一段生成过程能不能被另一位 agent 重放。

我们现在不只想重现一个二进制，还想让另一个团队或 agent 重现一组被接受过的产品行为。

这时，“谁是新的源代码”必须先问清楚：你到底想重现什么？

想重现的目标 对应的 source
同一份构建产物 源代码 + 依赖 + 构建工具链
同一次 AI 生成过程 prompt + 对话上下文 + 仓库状态 + 模型与工具；但结果仍可能不确定
同一组已验收的产品行为 生产规约 + 参考实现 + 验收 oracle（裁判规则）+ 环境与版本身份

所以，如果一定要在旧链路里找一个占据“源代码”位置的新东西：

它不是一句 prompt，也不只是单独一份 spec，而是发版时冻结下来的最小可重现闭包。

这时，“source”不应该按文件类型定义，而应该按可重现性定义：

在不知道原始对话、也不能依赖原作者记忆的情况下，能够让独立实现者重建目标行为，并判断是否重建成功的最小充分输入。

我暂时把它叫作一个项目的最小可重现闭包。这不是已经统一的业界术语，而是我对这个问题的工作定义。

它至少要闭合五件事：

组成 缺少以后会发生什么
Intent / scope 不知道要重现什么，也不知道明确不做什么
Constraints / decisions AI 会重新选择默认值、边界和技术取舍
Reference implementation / snapshots 失去当前真实行为这个可观察样本
Executable oracle / acceptance evidence 做完以后无法判断是否一致
Environment / version identity 同样输入在不同模型、依赖和配置下产生不同结果

因此，最小可重现单位既不是一句 prompt、一篇漂亮文档、完整聊天记录，也不只是代码仓库本身。它必须同时闭合可执行规约、参考实现、验收 oracle、环境与版本。

这并不是说代码不再是源码：

工件 仍然可以重现 无法单独重现
代码 当前实现与构建产物 产品意图、跨实现行为、验收标准
spec 目标行为与约束 非确定性模型最终生成的具体实现

因此，代码和 spec 都不是充分 source，还需要参考实现与可执行验收共同收口。

这也是“从代码反推规约”真正要补的东西：

它不是把代码降级成生成物，而是把代码上游丢失的意图与约束、以及代码下游缺失的证明，重新接回同一条可重现链路。

业界对已有原型的共同建议：不要急着重写

很多团队发现原型不够“生产级”以后，第一反应是重写。

但已有系统改造（brownfield modernization）、characterization testing，以及近期的 vibe-to-production 实践，正在收敛到相反的方向：先理解并固定现有行为，再逐步加固。

综合这些方法，可以把原地加固压成四步：

阶段 要做什么
Map 先看清现有系统真正有哪些部件和调用路径
Spec 把当前行为恢复成可以检查的约定
Characterization tests 固定当前重要行为，变化时立即发出信号
Foundations 最后再逐步补边界、契约和工程结构

这个顺序不能颠倒：

  • 没有 Map｜ spec 很容易描述一个想象中的系统；
  • 没有 Spec｜ 测试可能把偶然行为和 bug 一起冻住；
  • 没有 Tests｜ 重构等于关掉唯一能跑的版本后盲目重建。

原型不是一堆应该被丢掉的脏代码，而是当前唯一通过真实试验的行为样本。

再往生产走，旧工程世界其实早就准备了一部分答案

“另一套实现是否和参考实现一致”并不是 AI 时代才出现的问题。

旧工程世界已经积累了很多成熟手段：

旧方法 它解决什么 对 Vibe Coding 的启发
Characterization / Golden Master 固定旧系统当前实际行为 先记录原型做了什么，再谈重构
Contract Testing 检查模块或上下游之间的约定 prompt、schema、handoff 都可以成为契约
TCK / Conformance Test 同一规范允许多套实现 原型与生产不必同语言，只需满足同一行为集
Shadow / Parity Testing 新旧实现并行，对比真实输出 手写 case 之外，还要寻找未知差异
Content-addressed artifact 用内容哈希识别具体版本 不能只说“已同步”，要说同步到哪一版

这些方法擅长回答：

两份实现是否一致？

但它们默认另一个问题已有答案：

一致于什么？

当 Vibe Coding 让技术规约从未出现时，光有 parity 工具仍然不够，必须先重建被验证的标的物。

Harness Engineering：production artifact 怎样真正被 AI 使用

到这里还有一个缺口：即使规约和验收证据已经整理出来，如果部署侧 AI 只是“有空参考一下”，它们仍然可能变成一组无人消费的产物。

Harness Engineering 回答的不是“应该交付什么上下文”，而是“怎样让 agent 必须读取上下文、使用工具，并根据反馈完成工作”。它关注的不是让模型更聪明，而是给 agent 准备一套完整的工作回路：

阶段 Harness 要提供什么
开工前 正确、可导航的上下文
工作中 可以调用的真实工具
完成后 可计算的反馈与验证
出错时 能够阻断的 gate
遇到取舍 明确升级给人的判断边界

OpenAI 在关于 agent-first 工程的实践总结里提到，他们曾经尝试把所有说明塞进一个巨大的 AGENTS.md，结果很快遇到上下文拥挤、规则腐烂和无法机械验证的问题。

后来做法变成一套分层结构：

  • 入口要短｜ AGENTS.md 只负责导航；
  • 事实入库｜ repo 内结构化文档成为 system of record；
  • 按需读取｜ agent 根据任务渐进加载局部上下文；
  • 自动防腐｜ linter、CI 和 doc-gardening 检查 freshness；
  • 反馈入环｜ 测试、验证、review 和 recovery 编码进环境。

它与 production artifact 不是同一种东西：

Production artifact Harness
回答的问题 这个版本必须还原什么 AI 怎样被引导和约束着完成还原
主要内容 规约、源码指针、case、证据、版本身份 导航、工具、测试、反馈、gate、人工升级路径
在流程中的位置 一次发版携带的版本化输入 持续消费输入并检查结果的工作环境

两者接起来，交付才真正进入 AI 的工作回路：

production artifact 提供目标与证据 → agent 完成实现 → CI 计算验收结果 → release gate 决定能否上线

所以 Harness Engineering 对本文的落点，不是“业界也在从代码生成同一种 production artifact”，而是说明：Warrant 生成的产物不能停在一组文档里，它还必须接入部署侧的 agent、CI 和发版门禁。

给另一支团队交付，和给一个没有历史上下文的新 agent 交付，最终都需要明确边界、可导航证据、稳定接口，以及做错时马上响起的反馈。

社区现在争论的，也正是这些地方

这些路线并没有自动解决问题。社区争论仍然集中在四件事：

争议 核心问题
流程成本 会不会重新走回瀑布
Brownfield 已有代码怎样接入
生命周期 spec 怎样跟随实现演化
正确性 AI 如何证明自己真的做对

“The Waterfall Strikes Back”及其 Hacker News 讨论，集中体现了对流程官僚化和迭代成本的担忧。

Spec Kit 社区提出的 brownfield / spec refinement 问题，以及实现后调试如何重新回到 spec，则说明“第一次生成 spec”只是开始。

真正的分歧并不是“要不要写 spec”，而是它能否进入开发闭环：既不拖慢每一次探索，又能在关键边界被消费、被验证，并在过期时失效。

所以，业界趋势不是“重新开始写更多文档”

把这些路线放在一起，我看到的趋势更像这样：

正在发生的变化 对开发模式的影响
实现越来越便宜 人的价值上移到定义意图、边界和验收
产品人员可以直接操作 agent 产品与开发开始融合，但共识工作并没有消失
原型越来越容易直接成为产品 “先原型、后加固”会比“原型写完全部推倒”更常见
新 agent 随时可能接手 repo 必须同时具备 human legibility 与 agent legibility
文档成为机器输入 文档不能只好读，还要结构化、可定位、可 diff
AI 可以执行越来越长的任务 确定性的 gate、测试和 evidence 变得更重要

换句话说，软件开发的主流程正在重新分工：

过去更常见的主流程 AI 开发正在形成的主流程
人写需求 人定义意图、边界与验收标准
人写代码 AI 生成实现及配套资料
人检查最终结果 程序先验证确定性事实
各角色逐级移交 人集中处理取舍、例外与主观判断

产品不会因为产品人员开始写代码就消失，开发也不会因为 AI 开始写代码就消失。两者正在围绕 spec、reference implementation、tests、evidence 和 gates 重新分工。

“原型先行”很可能会留下来，因为做出可运行功能已经比准确描述它更快；但“两支团队长期人工维护两份实现”未必会一直存在。

如果条件允许，三种生产路径的优先级应该是：

优先级 生产路径
1 原型与生产共享同一份制品，通过门禁获得生产资格
2 根据可验证的 spec 重新生成另一份实现
3 人工逐项对照并迁移原型实现

即便第二份实现最终消失，反推规约、证据签收和声明防腐仍然有价值，因为三个月后的自己，以及没有上一轮上下文的新 agent，本质上就是下一位消费者。

04｜实践：我们正在用 Warrant 验证什么？

先说明它现在所处的位置：Warrant 还不是一套经过大量项目验证的标准答案，而是从这次真实交付中长出来的可运行雏形。它把前文的思考做成了 artifact、skills 和 gates，已经能在这个原型项目里跑通；但这些机制能否适应更多技术栈、团队边界和发布方式，仍然需要更多实战回答。

所以这一章更像一次公开的阶段记录：我们先把目前认为重要的结构做出来，也希望借此和更多 AI 开发者一起讨论——这种工具究竟应该以什么形态进入开发流程，哪些判断适合交给 Agent，哪些事实必须由程序复算，哪些责任仍然只能留给人。

什么项目值得做这套

你可能没有两个团队，也没有生产集群，但“下一位接手者”并不一定是部署团队：

下一位消费者 为什么需要这份上下文
三个月后的自己 已经忘记当时的取舍
新开的 AI 会话 拿不到上一轮完整对话
从 Cursor 换到 Codex 后的新 agent 工具和会话上下文已经变化
来修 bug 的同事 需要先区分正式行为与历史实现
把 demo 重做成 App 或服务的人 需要跨技术栈还原效果

只要下一次 AI 已经拿不到之前的完整对话，这个问题就已经发生了。当然，不是每个周末 demo 都值得上完整治理，可以按项目阶段逐步增加约束：

项目阶段 最小动作
一次性试验 什么都不做，保留速度
开始有人依赖 标出唯一正式入口和明确排除项
需要 AI 接手 生成阶段、数据流、配置和源码指针
需要另一套实现 加行为 golden 和验收证据
需要长期同步 加版本 hash、增量 diff 和失效 gate

最重要的不是一上来写二十份文档，而是在代码从“我刚跑通的东西”变成“别人要依赖的系统”那一刻，补上一份可以传递的技术理解。

也要先承认它的边界

边界 具体意味着什么
代码无法恢复真正的意图 它能说明系统现在做什么，却不能证明作者当初为何这样选择；工具可以准确提问，答案仍要由人给出
golden 只能证明已写入的义务 未真实触发的分支和未想到的边界仍可能遗漏，仍需更强的 characterization / dual-run
主观效果无法全部压成确定性 gate 路由、字段、配置和数据流容易验证；“生成内容是否真的打动人”仍需模型评审、人工判断和线上反馈
这套东西必须有消费者 如果没有另一个人、AI 或实现会使用规约，重型治理只会成为新的负担

到这里，才轮到 Warrant 出场

Warrant 就是这样从原型项目里长出来的。最开始，这些能力都集中在 pipeline-deploy-sync 里：

随着问题越补越多，我开始觉得，这不应该只是一套特定项目的部署脚本。真正具有通用性的，不是 manifest、golden 或 deploy packet 这些具体形式，而是它们背后的同一个问题：

一份今天正确的规约，怎样在它不再正确的那一刻自动暴露出来？

于是我把其中可能具有通用性的部分抽成了 Warrant，中文名叫「立据」。在新版 README 里，我把这次尝试压缩成了一句话：

把快速迭代的原型，交付成一份能检查、能同步、能验收、会随代码变化而失效的生产契约。

它目前尝试验证的核心，不是“从代码生成一套交接文档”，而是一条更窄、也更坚硬的规则：

每个重要声明，都要绑定它所描述对象的指纹；对象一变，旧声明就不再覆盖它。

它保护的不是某种文档格式，而是声明与现实之间的关系：

声明 它绑定什么 对象变化以后
“生产选择这个值，是因为……” baseline → chosen 取值对 旧理由自动过期，不能只改指纹糊弄过去
“这段设计已经由某人确认” 当前方案层的内容指纹 方案措辞变化，原确认自动失效
“这条行为已经被 case 证明” obligation、case 自声明和运行证据 少跑、错绑或只登记 case 都不能签收
“这里就是正式实现入口” file.py::symbol 源码指针 符号被移动或删除，gate 直接报错
“这次行为变化已经解释过” 当前行为快照 hash 新快照必须追加新的变更理由

这里还有另一类更隐蔽的问题：如果一项声明从来没有被写出来，就无从谈起“过期”。

所以当前 Warrant 又增加了 completeness 与 semantic-flow gates：多文件模块没有内部步骤，会被标为黑盒；router 没有真实分支、generator 没有输入输出契约、variant 没接到实际出口，也会被明确暴露。它试图避免一张漂亮的流程图用“看起来完整”掩盖声明本身过薄；这套检查是否足够、是否会造成新的流程负担，同样需要在更多项目里继续验证。

AI 负责起草和提问，人负责定夺，代码负责裁判

Warrant 仍然是不对称的两半，但中间那条人的边界现在更明确了：

工作 谁负责 为什么不能换人
确认交付 slice、沿正式入口追踪代码、起草结构与设计 AI skill 与人协作 范围和方案需要上下文，固定脚本只能猜
解释 why、处理代码中的矛盾、确认设计文字 人 代码能证明“现在怎样”，不能证明“为什么这样”
校验指针、指纹、集合覆盖、hash 和运行证据 确定性程序 这些结论必须可重复，不能被 AI 的解释说服

这也改变了 AI 遇到“不知道”时的处理方式。

代码与配置相互矛盾时，AI 不再挑一个更像的答案写进文档，而是生成 open_questions[]，把问题、影响和证据一起留在 artifact 里。设计层由 AI 起草后默认是未确认状态，只有人可以签字；设计内容一变，签字也随之过期。

换句话说，Warrant 允许三种诚实状态同时存在：

状态 它意味着什么
已证明 有可以机械复算的来源、指纹或运行证据
待确认 AI 已经起草，但还没有人对这段设计背书
待定夺 现有证据互相矛盾，必须把问题交还给人

这比让 AI 生成一份语气确定的“完整文档”更重要：空白和疑问不会消失在聊天记录里，也不会被排版洗成事实。

.warrant/ 现在记录的是一份可失效的设计

Warrant 的 canonical artifact 放在项目的 .warrant/ 目录中。它不是代码索引，也不是一份把所有细节都抄进来的技术手册，而是围绕一次正式交付，集中记录四件事：这条链路实际怎样运行、采用了什么方案、哪些问题仍待人决定，以及用什么 case 和 evidence 验收。

它还会把这份 artifact 与宿主仓库的 release 绑定起来：content_hash 标识交付的行为契约，原型 Git commit 定位产生这份契约的参考源码。这样，接手方拿到的不是一份脱离版本的说明，而是一个可以回到具体代码、继续检查并在变化后失效的版本。

技术文档也不再是 AI 重新读一遍代码后另写的一套材料。它只是这份 artifact 的一个可再生视图：

先从 artifact 渲染方案与结构 → 只按 evidence[] 补充被明确选中的代码证据 → 再生成给人阅读的 Markdown / HTML。

文档先讲方案、模型选型和语义流，代码细节只作为被明确引用的证据出现。artifact 没有记录方案，页面就显示“方案未记录”；分支没有被声明，renderer 也不会擅自根据函数顺序画出一条看起来合理的路线。

这时，技术文档、AI 使用的 bundle 和程序运行的 gate，不再是三套各自维护的材料，而是同一份 artifact 的不同消费方式。

Warrant 在这个坐标系里的位置

我不太想再给它发明一个新的流派名字。更准确地说，它把几条已经存在的路线接在了一起：

业界路线 Warrant 借用了什么 额外补了什么
SDD spec 是人和 AI 的共同工件 从已有代码反向起步，并让关键声明可以自动失效
Reverse SDD / intake 从代码恢复行为、约束与缺口 把无法恢复的 why 变成人机访谈和 open_questions
技术文档工程 为人呈现方案、结构与选型 文档只从 artifact 再生，未确认设计和空白也会被展示
Characterization / TCK 通过用例证明跨实现行为 case、obligation 与运行 evidence 双向校验
Harness Engineering 给 agent 稳定上下文、工具和反馈 skills 负责开放判断，确定性 gates 负责不可协商的裁判
Content-addressed artifacts / source provenance 用 hash 标识契约，用 Git commit 定位参考源码 支持增量 diff、同步握手和可验证的跨仓库源码定位

现在怎样试用 Warrant：先分清工具仓库和宿主仓库

Warrant 当前版本是 0.2.0，代码在独立的 Warrant 工具仓库中。新版首先明确了两个容易混淆的对象：

概念 它是什么 存放什么
Warrant 仓库 独立工具仓库 CLI 与 warrant-* skills
原型宿主仓库 正在被梳理和发版的业务项目 .warrant/、release bundle 与参考实现
生产宿主仓库 接住原型交付的业务项目 生产实现、运行 evidence 与 parity report

这三个对象的关系可以先用一张图记住：Warrant 工具本身不承载业务 artifact；artifact 和 release 属于原型宿主，生产侧通过 bundle 和 manifest 找到可复核的参考源码，再在自己的宿主仓库里完成 audit 与 sync。

推荐把 Warrant 当作独立工具安装，并不要求它成为业务仓库的 submodule；即使为了锁版本使用 submodule，Agent 的工作目录或 --root 也必须指向外层宿主，工具代码不能进入发版 slice。

具体安装方式和宿主配置见 Warrant README。安装完成后，只需要让 Agent 在真正的原型或生产宿主根目录里工作。

用法不是记命令，而是先认清自己在哪一侧

新版 README 把入口按责任角色分成了五种：

当前场景 在哪里打开 Agent 告诉 Agent 主要产物
原型第一次交付 原型项目 使用 warrant-onboard，梳理真正要发版的链路 .warrant/
先让人看懂方案 原型项目 使用 warrant-tech-doc，生成技术方案和网页 总览、模块文档、HTML
原型准备发版 原型项目 使用 warrant-release，检查并导出本次 bundle releases/<content_hash>/、源码定位、变更记录
生产第一次接手 生产项目，同时提供 bundle 使用 warrant-audit，先验证原型 commit，再审计生产实现 parity-report.json、未对齐项
生产跟进后续版本 生产项目，同时提供新版 bundle 使用 warrant-sync，读取契约 diff 与原型 commit 区间 依赖闭合的改动、运行证据

这张表就是 Warrant 的最小用法：先告诉 Agent 自己处在哪一侧、当前要完成哪种交付，再让它调用对应的 skill。具体命令、配置和门禁由 skill 与 CLI 共同完成，文章不再展开。

05｜延伸思考：原型与线上，可能只是一个暂时的边界

写到最后，也必须反过来怀疑一下这篇文章的前提。我们之所以需要一份 production artifact，是因为当前原型—线上模式里存在一条从原型责任域到线上责任域的生产交接。

但这条边界会一直存在吗？

如果未来原型可以直接上线，或者从头到尾都是同一个人和同一组 agent 在开发，我们还需要这份东西吗？重新梳理近两年的研究和工程实践后，我得到一个更谨慎的判断：

组织交接可以减少，但一项变化获得生产信任的过程不会自动消失。

先把已经发生的变化，与我们的想象分开

目前比较可靠的研究，至少说明了三件事：

已经观察到的变化 调研依据 它真正说明什么
AI 能提高局部代码产出，但不会自动提高整个组织的交付表现 DORA 2025把 AI 定义为组织能力的“放大器”；下游测试、评审和部署能力弱时，代码生成越快，失序也可能越快 不能只看代码生成速度，必须看完整反馈系统
人的工作开始从直接编写，移动到设计、审查和判断 Google 的工业实践观察到代码作者越来越像 reviewer；OpenAI 的 agent-first 实验则直接遇到了 human QA capacity 的瓶颈 “实现变便宜”有迹象，但判断与验收还没有被自动解决
Agent 自主运行越久，越依赖持久化工件和外部反馈 Anthropic 的长任务实验需要用进度文件、任务列表和 Git 状态跨越上下文；OpenAI 则把测试、日志、指标和架构约束编码进 repo prompt 更长、模型更强，并不能替代可恢复的上下文和可执行反馈

这些实践规模不同，远不足以证明软件工程已经进入统一的新范式，却共同否定了一个过于简单的叙事：

过度简化的想象 实际发生的变化
AI 会写代码，开发者就不再重要 人的工作上移到意图、设计、审查和判断
原型可以自然变成生产 review / test / deploy / observe 开始承受更多变化
代码生成更快，交付就会更快 原本隐藏在组织里的下游能力成为新的系统瓶颈

DORA 把这称为“放大器”很准确：AI 没有替团队决定开发范式，它只是把现有系统的优点和缺口同时放大。

到底什么在决定一种开发范式？

如果只用“瓶颈在哪里”解释开发范式，还会漏掉责任和验收。更完整地说，一种开发范式至少由三件事共同决定：

决定因素 要回答的问题
稀缺资源 当前最贵的是沟通、实现、判断，还是验证？
责任单元 谁对从想法到线上结果的整个链路负责？
验收机制 一次变化最终靠人的感觉、文档评审、自动化门禁，还是线上反馈获得信任？

把这三个维度放回不同的开发方式里，会比“人写还是 AI 写”更清楚：

开发方式 主要责任单元 主要事实源 变化怎样被接受
传统角色串行开发 产品、开发、测试等不同角色 需求单、技术方案、代码 跨角色评审与测试
Vibe Coding 原型 一个人与一次 AI 会话 可运行代码与作者记忆 作者直接体验效果
本文的原型 → 生产 原型侧与线上侧两个责任域 规约、参考实现、验收语料 parity gate 与生产签收
Agent-first 工程 对完整价值流负责的人—Agent 系统 repo 内的代码、知识、策略和状态 自动检查、人工判断与运行反馈共同闭环

所以，本文所说的“原型侧”和“线上侧”首先是责任域，不是组织架构。两边可以是同一个人、同一个仓库，也可以都由 AI 执行；只要判断成功的标准不同，边界就仍然存在：

原型责任域首先关心 线上责任域还必须关心
这个想法能不能跑通 它能否持续、稳定地跑
这一版效果对不对 所有正式路径是否仍然成立
作者能不能亲自验收 作者不在时，系统能否发现错误
修改是否让体验变好 修改能否审计、观测、回滚并解释影响

同一个人从“我觉得这一版对了”，切换到“我愿意让它持续服务真实用户”，也已经跨过一条责任边界。

两边都是 AI 也一样：负责生成变化的 agent 不能同时充当生产证据。证据必须来自生成叙事之外，例如测试、独立 gate、运行 trace、评测结果或人工判断。

“原型即线上”，其实有两种完全不同的意思

DevOps 和 Continuous Delivery 早就在尝试消除开发与运维之间的组织交接。

  • AWS 的 you build it, you run it让同一团队负责构建与运行；
  • DORA 对 Continuous Delivery 的定义要求软件在整个生命周期保持可部署，并让每次变化尽快得到质量和可部署性反馈。

这段历史给了“原型即线上”一个很重要的提醒：

减少 handoff 的成熟做法，从来不是取消验收，而是把验收从人工交接搬进自动化流水线。

所以，“原型即线上”需要拆成两层理解：

所谓“原型即线上” 是否正在发生 仍然缺不了什么
原型和生产使用同一份实现，不再由另一团队重写 已经是 Continuous Delivery 的常见方向 自动化测试、环境配置、发布门禁、可观测性
一次探索性修改只要效果不错，就可以直接被生产信任 目前没有可靠依据支持 风险边界、正式行为、失败恢复与线上证据

第一种完全可能，也比维护两套实现更理想；第二种则把“同一份代码”误当成“同一种责任”。代码可以不经过移交，责任不能不经过转换。更准确的未来形态，也许不是“原型直接等于生产”，而是同一份实现先在探索反馈里成为可用原型，再通过机器门禁与运行证据获得生产资格。

production artifact 在这里不会消失，只会改变形态。

它不再是一份交给另一个团队的 bundle，而会逐渐嵌入 CI、策略、observability 和 release state。

下一代交付物，可能是一项“带证据的变化”

这并非凭空出现的想象：

已有实践 交付时额外携带什么
Proof-Carrying Code 满足安全策略、可由接收方独立验证的证明
SLSA provenance 制品在何时、何地、通过什么过程产生的来源信息

它们解决的问题并不等同于产品行为验收：

  • Proof-Carrying Code 关注的是形式化安全策略；
  • SLSA provenance 关注的是软件供应链来源；
  • Warrant 关注的是意图、技术行为和跨实现一致性。

但三者共享一个很有价值的结构：生产者不只交付结果，还要同时交付接收方可以独立检查的依据。

沿着这个结构往前推，我更愿意把未来的软件交付单位称作 evidence-carrying change，即“带证据的变化”。

大多数产品行为无法被数学证明，因此“证据”比 proof-carrying change 中的“证明”更诚实。

它在不同开发模式里，会呈现为不同形态：

开发模式 “带证据的变化”怎样存在
跨团队、跨实现 production bundle
同团队、同实现 release candidate + 机器可读验收状态
更自主的 Agent 系统 agent 产生变化，gate 验证约束，线上信号决定阻断或回退

最后一种目前仍是推演，并非已经被研究证明的行业结论。

但调研至少让我更确定了一件事：

如果 Coding 最终成为项目里最廉价的环节，那么真正需要长期维护的“源码”，也许不再只是某一次代码实现，而是那套能够持续生成实现、约束变化并验证结果的上层上下文。

AI Coding 带来的深层变化，不只是把“写代码”交给 AI；它也在迫使软件开发把过去依赖角色、记忆和人工交接的判断，逐步编码成 Agent 可以读取、系统可以验证、运行环境可以反馈的控制回路。

Warrant 只是我们对这个变化的一次早期作答，而不是终点。如果未来原型侧与线上侧真的合并，今天的 bundle 形态可能会过时；即使边界仍然存在，artifact 的结构、Agent 与 CLI 的分工也很可能在更多实战中继续改变。

我更希望把这个雏形当作一个可以共同讨论的起点：一项变化怎样离开产生它的会话，带着足够的上下文和证据，进入真实用户所在的世界？如果这个问题成立，工具最终应该长成什么样，仍值得我们一起回答。
